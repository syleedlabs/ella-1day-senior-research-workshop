## [개념] 하네스 엔지니어링이란?

**하네스(Harness)** 란 AI 모델이 혼자서는 잘 못하는 부분을 보완하기 위한 **운영 구조**입니다. 같은 AI 모델이라도, **어떤 구조 안에서 일하느냐**에 따라 결과가 완전히 달라집니다. 이 운영 구조를 설계하는 것을 **하네스 엔지니어링**이라고 합니다.

### 얼마나 달라지길래 — 모델은 그대로 두고 환경만 바꾼 실험

`claude-code-harness` 라는 A/B 테스트가 있어요. **같은 모델**에게 **같은 실무 과제 15개**를 두 번 풀게 했습니다. 한 번은 `.claude/` 구성이 **없는** 폴더에서, 한 번은 에이전트 정의와 스킬이 **심어진** 폴더에서요.

| 어디서 풀었나 | 평균 품질 점수 |
|---|---|
| `.claude/` 구성 **없이** | 49.5 |
| `.claude/` 구성 **있을 때** | **79.3** (+60%) |

15개 과제에서 **15번 다 이겼고**, 특히 **어려운 과제일수록 격차가 벌어졌어요.** 가장 어려운 구간에서는 **+36.2점**이었습니다.

**모델을 더 똑똑한 것으로 바꾼 게 아닙니다.** 모델은 그대로 두고 **그 주변만 설계했는데** 이만큼 달라진 거예요.

📎 `revfactory/claude-code-harness` (Hwang, M.)

::: warning 이 숫자를 인용하실 땐 조건을 함께
**저자가 직접 측정한 결과이고 과제 수가 15개**예요. 제3자 재현은 아직 진행 중입니다.

방향은 분명하지만, 어디에 옮겨 적으실 땐 *"n=15 · 저자 자체 측정"* 을 같이 밝혀주세요. **오늘 배운 규칙 그대로예요** — 숫자엔 출처를, 확인 안 된 건 확인 안 됐다고.
:::

::: tip 나리님 폴더가 바로 그 "있을 때"입니다
`.claude/agents/` 여섯 개, `.claude/commands/` 아홉 개, 그리고 `CLAUDE.md`. 1-4에서 브리프가 **그 형태로** 나온 게 이것들 덕분이에요.
:::

## [개념] AI에게 일을 그냥 시키면 생기는 문제들

아래 내용은 Anthropic이 자체 기술 블로그에서 직접 공개한 것입니다. (2026년 3월 24일 발행)
원문: [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)

**문제 1: 컨텍스트 불안 — 대화가 길어지면 AI가 대충 마무리한다**

AI에게 긴 작업을 시키면, 처음에는 꼼꼼하게 수행합니다. 하지만 대화가 길어질수록 앞에서 무엇을 했는지 점점 헷갈리기 시작하고, **실제로 한계에 도달하지 않았더라도** AI가 *"이쯤이면 한계에 가까워졌겠지"* 라고 느끼면서 서둘러 끝내버리는 현상이 발생합니다. Anthropic은 이 현상을 **"컨텍스트 불안(Context Anxiety)"** 이라고 부릅니다.

**문제 2: 자기 평가의 함정 — AI에게 자기 결과물을 평가하라고 하면 항상 후하게 준다**

AI에게 콘텐츠를 만든 후 *"방금 만든 결과물을 평가해봐"* 라고 요청하면, 품질이 부족하더라도 *"아주 훌륭합니다!"* 라고 답하는 경우가 많습니다. **자기가 만든 것을 객관적으로 비판하는 것은 AI에게도 어려운 일**입니다.

::: warning 리서치에서는 두 번째가 특히 치명적이에요
브리프에 출처를 대충 붙여놓고 스스로 *"출처 표기 완료"* 라고 통과시키면, 나리님은 그걸 **검증된 자료로 알고 회의에 들고 들어가시게 됩니다.**
:::

## [개념] 해결책: 교대 근무 + Generator/Evaluator 역할 분리

**해결책 1. 컨텍스트 불안 → Context Reset (교대 근무)**

AI 에이전트 하나가 처음부터 끝까지 다 하지 않고, **구간을 나눠서 여러 에이전트가 교대로** 작업합니다.

에이전트가 일정 구간을 작업한 뒤, 진행 상태와 다음 할 일을 파일로 저장하고 **컨텍스트를 완전히 초기화**합니다. 그러면 새로운 에이전트가 해당 파일을 읽고 **깨끗한 상태에서 이어서** 작업합니다.

교대한 에이전트는 이전 컨텍스트가 없는 깨끗한 상태에서 시작하기 때문에, 뒷부분을 대충 처리하는 문제가 사라집니다.

::: tip 참고 — Compaction과는 다릅니다
Context Reset 외에 **Compaction(압축)** 이라는 방식도 있습니다. Context Reset은 **에이전트를 교체해서** 깨끗한 상태로 시작하는 것이고, Compaction은 **같은 에이전트가 계속 일하면서** 이전 대화를 요약·압축하는 것입니다. Compaction은 대화의 연속성은 유지되지만, **컨텍스트 불안 자체를 해결하지는 못합니다.**

1-2에서 배운 `/compact`가 Compaction, `/clear`가 Context Reset에 가까워요. 답이 이상해지기 시작하면 *"모델이 이상하다"* 가 아니라 *"컨텍스트가 찼구나"* 로 보시면 됩니다.
:::

**해결책 2. 자기 평가 편향 → Generator/Evaluator 분리**

설계하는 AI(**Generator**)와 채점 및 검수하는 AI(**Evaluator**)를 완전히 분리합니다.

여기서 한 가지 의문이 생길 수 있습니다. *"채점하는 AI도 어차피 AI인데, 역시 후하게 주지 않을까요?"*

맞는 지적입니다. 하지만 Anthropic이 발견한 핵심 인사이트는 이것입니다.

> **"자기 작업을 스스로 비판하도록 만드는 것"보다 "별도의 채점자를 엄격한 기준으로 세팅하는 것"이 훨씬 쉽습니다.**

리서치를 한 AI에게 *"객관적으로 평가해봐"* 라고 하면 어렵지만, **그 리서치에 관여하지 않은 별도의 AI**에게 명확한 채점 기준을 주고 *"이 기준에 맞는지 검수해줘"* 라고 하면 훨씬 신뢰할 수 있는 결과가 나옵니다.

핵심은 **Evaluator에게 구체적인 평가 기준을 정해주는 것**입니다. *"잘 만들었는지 봐줘"* 가 아니라, **"수치마다 📎 출처(매체 + 발행일)가 붙었는지, 그 숫자가 원문과 일치하는지, 국내 것과 해외 것이 섞이지 않았는지 확인해줘"** 처럼 명확한 기준을 제시해야 합니다.

## [개념] 실전 패턴: 3-에이전트 구조 (Planner / Generator / Evaluator)

위에서 다룬 문제와 해결책을 하나의 구조로 만든 것이 **3-에이전트 패턴**입니다. AI에게 복잡한 작업을 시킬 때, 하나의 AI에게 모든 것을 맡기는 대신 **기획/실행/검수 3단계로 역할을 나누면** 컨텍스트 불안과 자기 평가 편향을 동시에 해결할 수 있습니다.

```
Planner  ──▶  Generator  ──▶  Evaluator
기획자           실행자          검수자
                  ▲               │
                  └───────────────┘
                    기준 미달 시 재작업 요청
```

우리 파이프라인에선 이 **되돌아오는 화살표가 딱 한 번** 돕니다 (이유는 아래 토글에).

| 역할 | 하는 일 |
|---|---|
| **Planner** (기획자) | 사용자의 요청을 구체적인 작업 명세로 변환합니다 |
| **Generator** (실행자) | 실제 결과물을 생성합니다 |
| **Evaluator** (검수자) | 결과물을 평가하고, 기준에 미달하면 재작업을 요청합니다 |

:::: details 우리 파이프라인에 대입해 보기 — 역할 3개 · 검수 5항목 · 검수를 한 번만 도는 이유
::: tip 우리 비교 브리프 파이프라인에 대입하면
[2-1](/part2/2-1-agents)에서 본 5단계가 정확히 이 구조예요.

| 역할 | 우리 파이프라인에서 | 무엇을 하나 |
|---|---|---|
| **Planner** | 메인 대화 *(표 1번)* | 주제를 받아 **어느 소스를 볼지** 정함 |
| **Generator** | 조사원 둘 + 메인 대화 *(표 2·3번)* | 국내·해외를 나눠 조사하고, 요약을 **시차 렌즈로 해석해 브리프를 씀** |
| **Evaluator** | `senior-source-check` *(표 4번)* | 📎 출처·수치·국내해외 혼동·미확인 라벨을 검사하고 **지적만 돌려줌** |

**검수자는 브리프를 직접 고치지 않습니다.** 지적만 하고, 고치는 건 Generator 몫이에요. 그래야 *"만든 쪽"* 과 *"보는 쪽"* 이 안 섞입니다.
:::

::: warning 검수자가 보는 다섯 가지
| # | 검수 질문 | 무엇을 막나 |
|---|---|---|
| **1** | 모든 수치에 **📎 출처(매체 + 발행일)** 가 붙었나? | 출처 없는 숫자가 사실처럼 읽히는 것 |
| **2** | 그 숫자가 **원문과 실제로 일치**하나? | 단위 착오 (억↔조), 연도 착오, 반올림 왜곡 |
| **3** | **국내 것과 해외 것이 섞이지 않았나?** | 일본 시장 규모를 국내 수치로 옮겨 적는 사고 |
| **4** | 확인 못 한 항목에 **⚠️ 미확인**을 붙였나? | 모르는 걸 아는 척 넘어가는 것 |
| **5** | 시차가 **외운 상수가 아니라 계산된 값**인가? | *"일본은 우리보다 O년 앞선다"* 를 근거 없이 단정하는 것 |

**3번과 5번이 이 검수자에만 있는 항목**이에요. 국내·해외를 동시에 조사하고 시차를 계산하는 파이프라인이라, **두 나라 숫자가 섞이는 사고**와 **시차를 외워서 쓰는 사고**가 고유 위험이거든요.

검수자 파일에는 이렇게 적혀 있습니다 — *"애매하면 통과시키지 않는다. 검수자의 기본값은 보류다."*

다만 **원문까지 직접 열어 대조하는 건 최대 세 건**으로 정해뒀어요. 결론을 떠받치는 수치, 단위가 큰 수치, 시차에 쓴 도달 연도 — 이 셋입니다. 나머지는 문서만 보고 판정해요.
:::

::: tip 검수는 **한 번만** 돕니다 — 일부러 그렇게 해뒀어요
"기준에 미달하면 재작업"을 **통과할 때까지 반복**하게 걸어두면 그럴듯해 보이죠. 그런데 실제로 돌려보면 두 가지가 생깁니다.

- **끝나지 않습니다.** 검수자의 기본값이 "보류"라 트집 잡을 거리는 늘 남아요. 나리님은 화면 앞에서 계속 기다리시고요.
- **고칠수록 얇아집니다.** 지적을 피하려고 확실한 문장만 남기다 보면, 정작 쓸모 있는 해석이 깎여 나가요.

그래서 우리 파이프라인은 **지적을 한 번 받아 고치고 끝냅니다.** 그러고도 안 풀린 건 `⚠️ 미확인`으로 옮겨 적어요.

> **완벽하게 맞는 브리프보다, 어디가 불확실한지 표시된 브리프가 낫습니다.** 앞은 만들 수 없고 뒤는 만들 수 있거든요.
:::

## [개념] 핵심 교훈 3가지

| 교훈 | 내용 |
|---|---|
| **1. 에이전트를 직접 관찰하라** | AI가 작업하는 과정을 직접 지켜보세요. 어디서 막히는지, 어떤 판단을 내리는지 확인하고, 원하는 결과가 나올 때까지 `CLAUDE.md`나 프롬프트를 조정하세요. |
| **2. 복잡한 작업은 분해하고 전문화하라** | 하나의 AI에게 모든 것을 시키는 대신, 기획/실행/검수처럼 **역할별로 전문 에이전트를 배치**하면 전체 성능이 올라갑니다. |
| **3. 새 모델이 나오면 하네스 구조를 다시 점검하라** | AI 모델이 발전하면 불필요해진 구성요소는 제거하고, 새롭게 가능해진 기능을 위한 구성요소를 추가하세요. 점검하지 않으면 **불필요한 절차만 쌓이게** 됩니다. |

## [정리] 우리 파이프라인 설계 한 장 요약

Part 2를 여기까지 오시면서 설계 근거가 챕터마다 하나씩 나왔어요. **한 장에 모아둡니다.**

| 왜… | 이유 | 자세히 |
|---|---|---|
| **왜 일본을 보나?** | 일본은 우리가 앞으로 겪을 일을 **이미 겪었다.** 무엇이 통했고 무엇이 실패했는지가 나와 있음 | [1-4](/part1/1-4-agent) |
| **왜 시차를 매번 계산하나?** | 한국이 더 빨라서 **시차가 계속 줄고 있음.** 외운 숫자를 쓰면 틀림 | [1-4](/part1/1-4-agent) |
| **왜 국내·해외를 나눠 조사하나?** | ① 동시에 돌아 **시간 절반** ② 두 나라 자료를 한 머리에 넣으면 **숫자가 섞임** | [2-1](/part2/2-1-agents) |
| **왜 출처에 발행일까지 붙이나?** | 시니어 시장은 빠르게 변함. **3년 전 숫자를 오늘 것처럼 쓰면** 없는 기회를 쫓게 됨 | [2-2](/part2/2-2-prd) |
| **왜 모르는 걸 ⚠️ 미확인이라 쓰나?** | 리서치는 **틀리면 사업 판단이 틀어짐.** 근거 없는 단정보다 "모른다"가 나음 | [2-2](/part2/2-2-prd) |
| **왜 검수자가 따로 있나?** | **만든 쪽이 검사하면 후해짐.** 결과물만 받은 눈이라야 냉정함 | 2-4 (이 챕터) |

::: tip 하나로 줄이면
**"똑똑함보다 정직함."**

이 표의 여섯 줄이 전부 같은 곳을 향해요 — 화려한 결과보다 **틀리지 않는 결과**. 나리님이 이 브리프를 회의에 들고 들어가실 수 있어야 하니까요.
:::

## [한 걸음 더] 루프 엔지니어링

코딩 에이전트에게 **프롬프트를 보내는 대신 "루프를 설계하라"** 는 말이 자주 들립니다. Claude Code 팀은 루프를 네 가지로 정의했어요.

| 루프 | 무엇이 시작시키나 | 도구 |
|---|---|---|
| **① 턴 기반** | 나리님의 프롬프트 | 커스텀 스킬 |
| **② 목표 기반** | 나리님의 프롬프트 (목표 달성까지 반복) | 목표를 문장으로 주고 반복시키기 |
| **③ 시간 기반** | 정해진 시각 | `/loop` · `/schedule` |
| **④ 프로액티브** | 이벤트·일정 (사람 없음) | 위 전부 |

**1-4에서 하신 건 전부 ①번**이에요. 커맨드를 치면 시작되고, 에이전트가 "다 했다"고 판단하면 끝납니다.

*"주간 리포트를 매주 월요일 아침에 알아서 돌게 하려면?"* 이 궁금해지시면 ③번이에요. 거는 방법은 클로드 코드에게 *"주간 리포트를 매주 월요일 아침 8시에 돌려줘"* 라고 말씀하시면 알아서 안내해 줍니다.

::: warning 순서를 건너뛰지 마세요
**하네스를 먼저 세우고 루프를 겁니다.** 검증 기준 없이 자동 반복을 걸면 **나쁜 결과물이 자동으로 쌓여요.** **방금 이 챕터에서 세운 게 바로 그 하네스**예요. 루프는 워크숍이 끝난 뒤에 손대셔도 늦지 않습니다.
:::

각 유형을 언제 쓰는지, 토큰은 어떻게 관리하는지는 → [Claude Code 루프 엔지니어링 가이드](https://www.modernweblabs.com/ko/insights/claude-code-loop-engineering)
